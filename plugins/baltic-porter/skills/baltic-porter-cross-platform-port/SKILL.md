# Three platforms, one port

Version: written against Baltic Porter engine master `ab8e129d`. The consumer pins the engine in
`project/plugins.sbt` as `"com.kubuszok" %% "balticporter-engine" % "<full commit hash>-SNAPSHOT"`.

A green JVM compile says nothing about the other two rows. Scala.js compiles everything and fails at
LINK on an unknown method; Scala Native links whole classes and fails on a method its javalib never
declared. Every platform question is answered the same way: read the javalib, then decide.

## 1. Check the javalib, do not guess

```
J=$(find ~/Library/Caches/Coursier/v1 -name 'javalib_native0.5_3-*.jar' | sort | tail -1)
unzip -l "$J" | grep 'java/net/'                       # Native: which classes exist
JS=$(find ~/Library/Caches/Coursier/v1 -name 'scalajs-javalib-*.jar' | sort | tail -1)
unzip -l "$JS" | grep 'java/lang/ThreadLocal'          # JS: is the class present?
unzip -p "$JS" java/lang/ThreadLocal.sjsir | strings | grep -i withInitial   # JS: is the member present?
```

(On Linux the Coursier cache is `~/.cache/coursier/v1`.) A `Foo$.sjsir` / `Foo$.nir` entry is the
companion: no companion, no static factory.

Measured so far (Scala.js 1.22, Scala Native 0.5.11/0.5.12):

- `java.net.URL`: absent on BOTH (Native ships `URI`, `URLEncoder`/`URLDecoder`,
  `MalformedURLException`). `Class#getResource` returns a `URL`, so it is unusable on both;
  `Class#getResourceAsStream` exists on Native (and answers null: no resources are linked in) but not
  on Scala.js.
- `ThreadLocal`: the class exists on both; the `withInitial` factory on Native only. Spell
  `new ThreadLocal[T] { override def initialValue(): T = e }`, never `ThreadLocal.withInitial`.
- `java.lang.invoke` (`MethodHandle`) and reflection (`Class#getMethod` …): JVM only.

## 2. What the engine already knows, and where it says so

- The engine records per-API platform availability in its catalog
  ([`ApiRows.scala`](https://github.com/kubuszok/balticporter/blob/master/balticporter/api/src/main/scala/balticporter/catalog/ApiRows.scala))
  and flags JVM-only use with
  [`PortabilityCheck`](https://github.com/kubuszok/balticporter/blob/master/balticporter/engine/src/main/scala/balticporter/tir/PortabilityCheck.scala).
  Read them to see whether a fact is already recorded. A missing or wrong row is an engine fix:
  report it to the engine repository with the javalib evidence from section 1.
- In the run's `findings.tsv` / `report.md`: `portability(all|emitted|injected)` lists JVM-only API
  sites (`injected` non-zero means a replacement YOU ship is unportable), and `remediation` groups
  them into the seam that would fix most of them. See `baltic-porter-read-port-issues`.

## 3. The port's answer is policy

In the order to try:

- respell a call with `call-site-substitution` (for example `getResource(x) != null` →
  `getResourceAsStream(x)`, closed and null-checked);
- drop the type and inject a portable replacement (`dropTypes` + `inject` or `providedSources`);
- per-platform answers: `platformDirs` (a directory per row `jvm` / `js` / `native` that only that
  row compiles), or `rowSources` when the upstream itself ships a platform emulation of a class (a
  GWT `emu` tree);
- narrow `targets` WITH a stated reason, only when the library genuinely cannot run there.

Never a JVM-only dependency in the consumer (no jackson, ANTLR or reflection to make a row pass).
"Keep it hand-maintained" is not an answer. The keys are documented in
[Configuring a port](https://github.com/kubuszok/balticporter/blob/master/docs/user-guide/configuring-a-port.md)
and `baltic-porter-customize-port`.

## 4. The reference port already decided most of it

Before inventing a spelling, read what the reference hand port shipped at that site:
`git -C ../sge show origin/master:<path>` (or the hand port's git history if the file has since been
replaced by generated code). Its migration notes often name the platform decision (for example
`ThreadLocal … NOT the withInitial static factory`, a Scala.js link regression). The port should emit
the same spelling, with Java's behaviour.

## 5. Verify on every row before pushing

sge: `testCompile-jvm-3; testCompile-js-3; testCompile-native-3`, then `ci-jvm-3`, `test-js-3`,
`test-native-3` (or `verifyLocal`, which runs all three). Native tests link: a suite that compiles
can still fail to link, so the Native TEST run is the gate for injected code. Fixture differences
between rows are real (`DummyTextureData.type` vs `dataType`): fix the fixture, never skip the row.

## 6. Behaviour: Java wins, on every platform

A Native suite expecting a different exception than Java (`FileReadError` vs `GdxRuntimeException`)
is the hand port's divergence: the port keeps Java's behaviour and the test is adapted, recorded as a
finding. JVM-only fallbacks (classpath resources) stay counted on JS.
