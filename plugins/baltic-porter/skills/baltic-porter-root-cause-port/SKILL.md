# Root cause, not symptom

Version: written against Baltic Porter engine master `ab8e129d`. The consumer pins the engine in
`project/plugins.sbt` as `"com.kubuszok" %% "balticporter-engine" % "<full commit hash>-SNAPSHOT"`.

A generated line is the output of a chain of decisions, and the run's report tables name every
link. Read them in this order and stop at the first that explains the spelling. The report of each
port is `<reportDir>/run-latest/`, where the generator sets `balticporter.reportDir` (sge:
`target/balticporter-reports/<label>/`, ssg: `target/balticporter/port-report/<label>/`; read
`project/BalticPorterGen.scala` for the others). What every file holds is in
[Reading the report](https://github.com/kubuszok/balticporter/blob/master/docs/user-guide/reading-the-report.md);
`baltic-porter-read-port-issues` is the condensed version.

## 1. Locate the error, never read the emitted file by hand

`srcmap.tsv` maps every emitted member's line range to the Java file and line it came from
(`unit  member  kind  start  end  javaPath  javaLine  digest`). For an error at line `L` of the file
for top-level unit `U`:

```
awk -F'\t' -v u='<U>' -v l=<L> '$1==u && $4<=l && l<=$5' <reportDir>/run-latest/srcmap.tsv
```

The narrowest matching row is the member. To sort a whole compiler log at once, the engine jar
ships `balticporter.tir.CorrelateMain` (`--srcmap [main=|test=]<srcmap.tsv> --scalac <log> --out
<dir>`), which writes `errors.tsv` with one of four lanes per error: `EngineGap` (located to a member
and its Java), `Approx` (a region the engine marked approximate), `Declared` (the engine's own
`compiletime.error` under `preview = true`) and `Unmapped` (a file the source map does not cover: an
injected or hand-written file — the fix is in that file, not in the engine).

One `Unmapped` error can STOP the compile before the port's own sources are typed: a count of "1
error" may be measuring nothing. Read the first error first.

## 2. The decision behind the member

```
grep 'Owner#member' <reportDir>/run-latest/decisions.tsv       # kind, reason, phase, manifest key
grep 'Owner#member' <reportDir>/run-latest/port-map.tsv        # upstream -> emitted name and disposition
grep 'Owner#member' <reportDir>/run-latest/findings.tsv        # refusals, each naming its guard
grep 'Owner#member' <reportDir>/run-latest/derived-policy.tsv  # what a reference port spelled there (when derive is on)
grep -rn 'porter:' <portRoot>/src_managed/…/Owner.scala         # the same decisions, beside the code
```

Match on the upstream (Java) name as well as the emitted one: decision and policy keys are written
in the upstream namespace. A frozen derived policy is a committed file in the consumer (sge:
`sge-port/*derived-policy.tsv`).

A `policy` finding says which key never matched or which guard refused, and that sentence IS the
cause (for example `the component reaches java.util.Comparator#compareTo`). A key that "matched and
the rule did nothing" is usually a question of ownership: the member belongs to a type this run does
not emit (a JDK or third-party type, or a base module's type), whose signature no phase may move.

To tell whether a phase touched a declaration at all, use the kill switch
(`balticporter.skipPhases`) and compare `members.tsv` digests between the two runs; see
[Debugging a port](https://github.com/kubuszok/balticporter/blob/master/docs/user-guide/debugging.md).
With `sbt --client`, set flags in `.balticporter/debug.properties` (the server does not see `-D` or
the environment), and clear them when done.

## 3. Compare with the reference spelling

The reference is the hand port the generated code replaces. In sge it is master's hand-written
tree or its git history: `git -C ../sge show <ref>:<path> | grep -n <member>`. It is the spelling
the port owes (API parity) and often carries the migration note that explains it. A consumer file
patched away from the reference is a symptom; the reference text is the test. Behaviour follows Java
even where the hand port differed.

For a dependent port (sge over lls, an extension over sge-core), also compare the base's
`port-map.tsv`: a dependent resolves against the base's Java and follows the base's published
renames, so a spelling can come from the base's policy.

## 4. Which kind of fix

| kind | what it means | where the fix goes |
|---|---|---|
| (a) universal | a fact about Java and Scala, true of every library | the engine, unconditional, with a test. Not this repository: report it (or open a PR) at <https://github.com/kubuszok/balticporter> |
| (b) configured | the engine's mechanism exists; this library supplies values | this repository's `.conf` / manifest / policy code (`baltic-porter-customize-port`) |
| (c) library-specific | knowledge that only ever applies to this library | a `Phase` + `TransformFactory` in this repository, or an injected file |

A shape that recurs in a consumer (`Nullable[java.lang.Integer]` sixteen times in one class) is a
mechanism, not sixteen patches. Most things that look library-specific are (b) with the policy
written inline. The engine's own statement of the three kinds is in
[Customizing the translation](https://github.com/kubuszok/balticporter/blob/master/docs/user-guide/customizing-translation.md#three-kinds-of-rule).
Java constructs that compile to different Scala behaviour (and are therefore engine bugs when they
appear) are listed in
[Java semantics Scala does not share](https://github.com/kubuszok/balticporter/blob/master/docs/user-guide/java-semantics.md).

A policy change that alters what an EXTERNAL type spells (a member rename on a redirected JDK type)
is easiest to check first on a `balticporter.testkit.PortSuite` test with a Java snippet, before
regenerating the whole consumer.

## 5. Measure the fix where it can be seen

- A change to a base port (lls, sge-core) moves the base's published port map: regenerate the base
  before its dependents (otherwise a dependent prints `BASE SURFACE (contract questions this run
  could not answer)` and fails with `contract question(s) shaped emitted text and could not be
  answered from a base's published port map`).
- The consumer's `testCompile-*` and test rows are the measurement. `members.tsv` before and after
  shows the blast radius without a compiler: every changed digest should be one you expected.
- State the before → after numbers (errors, findings, failing tests) in the commit message.
